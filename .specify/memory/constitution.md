# Конституція навчального Java-застосунку «Кол-центр»

## Core Principles

### I. Мінімальна складність
Архітектурні та програмні рішення MUST бути мінімально складними й відповідати
навчальній меті та поточним вимогам. Заборонено вводити зайві рівні абстракції,
залежності чи інфраструктуру без обґрунтованої потреби.

### II. Єдина відповідальність класу
Кожен клас MUST мати одну чітко визначену відповідальність відповідно до
принципу єдиної відповідальності (SRP). Зміни для різних причин мають бути
локалізовані у відповідних класах.

### III. Імітація зовнішніх операцій у консолі
Замість реального виконання зовнішніх операцій методи MUST виводити в консоль
повідомлення, що описують очікувану дію. Застосунок не виконує зовнішніх
викликів як частину цієї навчальної реалізації.

### IV. Запуск із командного рядка без зовнішньої інфраструктури
Компіляція та запуск застосунку MUST виконуватися виключно з командного рядка.
На цьому етапі застосунок MUST NOT використовувати зовнішні сервіси чи бази даних.

### V. Впровадження залежностей через екземплярні механізми
Впровадження залежностей MUST виконуватися через конструктори або setter-методи.
Статичні методи MUST NOT використовуватися для впровадження залежностей.

## Технологічні та мовні обмеження

Імена класів, методів, атрибутів та інших програмних елементів MUST бути
англійською мовою. Коментарі до коду та пояснення MUST бути українською мовою.

## Робочий процес і документація

Специфікація проєкту MUST вестися українською мовою. UML-діаграми MUST
зберігатися в каталозі `docs` у текстовому форматі.

## Governance

Ця конституція є обов'язковою для проєктних специфікацій, планування,
реалізації та перевірки змін. Відхилення від принципу MUST бути явно
обґрунтоване у відповідній специфікації або документації та погоджене до
реалізації.

Зміни до конституції вносяться через перегляд цього документа. Кожна зміна
MUST мати визначену версію, оновлену дату останньої зміни та Sync Impact
Report для перевірки впливу. Версії MUST відповідати семантичному
версіонуванню: MAJOR — несумісні зміни принципів або правил; MINOR — нові
принципи чи суттєве розширення вимог; PATCH — уточнення без зміни змісту
зобов'язань.

Під час перевірки кожної зміни MUST звіряти її відповідність цій конституції,
зокрема межі відповідальності класів, простоту рішення, консольну симуляцію
зовнішніх операцій, правила запуску, впровадження залежностей та мовні й
документаційні вимоги.

# Дослідження: UML-документація кол-центру

## Висновок

Специфікація визначає цільові формати, шляхи, предметну область, ключові зв’язки та критерії приймання. Невирішених технічних уточнень, що блокують планування, немає. Функція створює документаційні артефакти, а не реалізацію Java-застосунку.

## Рішення

### Текстові формати діаграм

- **Рішення**: use case diagram буде у PlantUML (`docs/usecase.puml`); class, sequence та state diagrams — у Mermaid (`docs/class.mmd`, `docs/sequence.mmd`, `docs/state.mmd`).
- **Обґрунтування**: це точні формати й шляхи з FR-002, FR-004, FR-010 та FR-012. Текстові джерела можна зберігати у `docs/` відповідно до конституції та переглядати засобами, сумісними з кожним форматом.
- **Розглянуті альтернативи**: один формат для всіх діаграм або графічні файли. Відхилено, оскільки суперечить заданим форматам/розширенням або не зберігає обов’язкове текстове джерело.

### CRC-картки

- **Рішення**: створити `docs/crc.xlsx` з окремою карткою для кожного класу класової діаграми, включно з абстрактним і службовими класами; інтерфейс не включати як клас.
- **Обґрунтування**: так виконуються FR-013, SC-005 та явно сформульоване припущення специфікації про картку для кожного класу.
- **Розглянуті альтернативи**: картка лише для кожної доменної сутності або картки для інтерфейсів. Перше залишило б без покриття службові/абстрактні класи; друге не відповідає визначенню картки для кожного класу та припущенню про інтерфейс.

### Межі моделі й інтеграцій

- **Рішення**: описати лише документаційну модель навчального Java-застосунку; телефонію та пошту показати як симульовані сервіси, залежності передавати через екземплярні механізми.
- **Обґрунтування**: відповідає припущенням специфікації та принципам I, III, IV і V конституції.
- **Розглянуті альтернативи**: реальні зовнішні сервіси, база даних або фактична реалізація Java-коду. Відхилено як позамежові для функції та несумісні з конституцією.

### Зовнішні контракти

- **Рішення**: каталог `contracts/` не створювати.
- **Обґрунтування**: результат функції — внутрішня документація предметної області, а не API, CLI-команда чи контракт взаємодії між системами.
- **Розглянуті альтернативи**: окремі контракти сервісів телефонії/пошти. Відхилено: сервіси в цій функції лише моделюються, реальної інтеграції немає.

## Перевірка невідомих

Версія Java, конкретні версії PlantUML/Mermaid і вибір XLSX-редактора не потрібні для визначення формату чи створення планових артефактів: специфікація не вимагає запускати Java-програму або додавати залежності. Під час перевірки достатньо засобів, сумісних із заданими форматами; їх встановлення не є частиною функції.

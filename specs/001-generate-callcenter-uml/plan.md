# План реалізації: UML-документація кол-центру

**Гілка**: `001-generate-callcenter-uml` | **Дата**: 2026-10-08 | **Специфікація**: [spec.md](spec.md)

**Вхід**: специфікація функції `specs/001-generate-callcenter-uml/spec.md`

## Підсумок

Створити в `docs/` чотири узгоджені текстові UML-діаграми у визначених PlantUML/Mermaid форматах і книгу `crc.xlsx` з карткою для кожного класу на діаграмі класів. Діаграми описують один наскрізний процес: заявка клієнта, обробка дзвінка оператором, запис і оцінювання розмови, підготовка та надсилання підсумку. Модель дотримується SRP та інверсії залежностей через екземплярне впровадження; телефонія й пошта показані як симуляції.

## Технічний контекст

**Мова/версія**: Java — мова предметної моделі навчального застосунку; реалізація Java-коду поза межами цієї функції.

**Основні залежності**: PlantUML для `usecase.puml`, Mermaid для трьох файлів `.mmd`; сумісний із XLSX засіб перегляду для CRC-карток. Жодна залежність виконання застосунку не додається.

**Зберігання**: текстові файли діаграм і `docs/crc.xlsx`; база даних не потрібна.

**Перевірка**: перевірка рендерингу відповідними засобами та звірка структури й змісту з вимогами FR-001—FR-016 і критеріями SC-001—SC-006.

**Цільова платформа**: міжплатформні засоби перегляду PlantUML, Mermaid і XLSX; застосунок не запускається в межах цієї функції.

**Тип проєкту**: документаційні артефакти для навчального Java-застосунку.

**Цілі продуктивності**: не застосовуються.

**Обмеження**: точні шляхи та формати з FR-002, FR-004, FR-010, FR-012 і FR-013; українські пояснення, англомовні програмні ідентифікатори; жодних реальних викликів телефонії, пошти чи баз даних.

**Масштаб**: чотири діаграми, одна книга CRC, наскрізний процес із трьома бізнес-операціями та картками для всіх класів моделі.

## Перевірка конституції

| Принцип | Перевірка плану |
|---|---|
| Мінімальна складність | Створюються лише обов’язкові діаграми та CRC-картки; інфраструктура й залежності виконання не додаються. |
| Єдина відповідальність класу | У діаграмі класів кожному класу призначається окрема відповідальність; зв’язки ілюструють розподіл роботи між учасниками та службами. |
| Імітація зовнішніх операцій у консолі | Телефонія й електронна пошта моделюються як очікувані дії без реальних інтеграцій. |
| Запуск без зовнішньої інфраструктури | Функція обмежена документацією; бази даних та зовнішні сервіси відсутні. |
| Впровадження залежностей через екземплярні механізми | `Call` отримує `TelephonyService` через конструктор; статичне впровадження не моделюється. |
| Мовні та документаційні правила | Пояснення українською, ідентифікатори англійською, текстові джерела діаграм у `docs/`. |

**Початковий gate**: пройдено. Виявлених суперечностей із конституцією немає.

## Підхід до перевірки й ризики

- Перевірити наявність усіх п’яти файлів у точних шляхах і можливість відкрити/відрендерити кожен засіб свого формату.
- Зіставити сценарії, імена учасників, класів, методів і стани між діаграмами та картками; окремо перевірити успішний ланцюжок `NewRequest` → `CallInProgress` → `Recorded` → `QualityEvaluated` → `SummarySent`.
- Звірити вимоги до класової діаграми: абстрактний клас, інтерфейс і реалізація, узагальнення, залежність, композиція, члени/конструктори, `final`, перевизначення й перевантаження.
- Звірити CRC-покриття з класами діаграми: одна картка на клас із точними заголовками колонок, обов’язками та співробітниками (або явною відсутністю співробітників); інтерфейс як клас не карткується.
- У помилкових гілках не позначати операцію успішною: відсутність оператора/запису/підсумку або невдала доставка не повинні просувати процес у наступний успішний стан.

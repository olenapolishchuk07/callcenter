# Дослідження та технічні рішення

## Рішення

- **JDK та Maven**: зберегти наявну конфігурацію Maven із `maven.compiler.release=21` і наявні залежності SQLite JDBC та JUnit. Додати лише бібліотеки для зазначених HTTP, JSON і журналювання.
- **Google Guice 7**: зберегти constructor injection `RecordingStore` у `Call`; додати binding `WebServer` → `JavalinWebServer`. Singleton залишити для інфраструктурного вебсервера й SQLite-з'єднання, не для доменних об'єктів.
- **Javalin 6**: запустити вбудований сервер на `8080`; визначити API-маршрути та віддачу classpath-ресурсів `/public` в `JavalinWebServer`. Залишити цей клас єдиною залежністю від Javalin.
- **JSON**: використовувати Jackson `ObjectMapper` тільки всередині `JavalinWebServer`. Контракт API передає `createdAt` як ISO-8601 local date-time рядок; це не вимагає JSON-реєстрації Java Time модуля. Некоректний JSON та невалідні поля мають повертати JSON-повідомлення, а не неструктуровану сторінку помилки.
- **Журналювання**: додати `slf4j-simple` як SLF4J provider у версії, сумісній з API Javalin; логувати запуск сервера та інфраструктурні помилки. Не показувати stack trace або внутрішні деталі сховища у відповіді користувачеві.
- **SQLite**: лишити таблицю й SQL у `SqliteRecordingStore`, розширивши наявний `RecordingStore` окремими операціями вставлення, пошуку, оновлення та видалення, щоб дубль не перезаписував запис, а PUT відсутнього ID не створював його. Не використовувати наявний upsert `save` як HTTP create/update.
- **Фронтенд**: обрати vanilla HTML/CSS/JavaScript без додаткової CSS/JS бібліотеки. Розмістити сторінку у `src/main/resources/public`; безпечний показ даних робити як текст, підтвердження видалення — до запиту, темний стиль — у CSS.
- **Множинність моделі**: `Call` керує колекцією `CallRecording` з множинністю `0..*`, як уточнив користувач. Це рішення узгоджує CRUD-перелік FR-009 із власною колекцією моделі; припущення специфікації про `0..1` має бути оновлене у відповідній UML-діаграмі під час реалізації.
- **Помилки**: використати визначені FR-012 статуси `400`, `404`, `409` та успішні статуси `200`/`201`. Для помилки SQLite передбачити `500` із українським JSON-повідомленням відповідно до FR-020; не трактувати помилку як успіх.

## Обґрунтування

Рішення зберігають задані конституцією межі: домен і контролер не знають Javalin чи HTTP, SQL не виходить зі сховища, а вебсторінка не дублює серверні правила. Наявний Maven-проєкт уже використовує JDK 21, Guice, SQLite та JUnit, тож нова структура обмежується MVC, адаптером HTTP/JSON і трьома статичними ресурсами. Явні `insert`/`update`/`delete` усувають небезпечне для контракту поводження наявного `save`, яке зараз виконує upsert.

Поточна документація Javalin описує 7.x, тому під час реалізації треба орієнтуватися на Javalin 6 API й не переносити зміну реєстрації маршрутів, специфічну для 7.x. Для фіксації сумісної лінійки в Maven використовувати версію 6.x; Javadoc 6.7.0 доступний окремо.

## Альтернативи

- **Javalin 7** відхилено, бо специфікація прямо вимагає Javalin 6.
- **`javalin-bundle`** відхилено, бо він включає додаткові компоненти; окремі залежності краще відповідають вимозі використовувати `jackson-databind` і `slf4j-simple`.
- **Jackson-модель із прямим `LocalDateTime` binding** не обирається: рядковий DTO-контракт простіший і не потребує додаткового Java Time модуля.
- **Оновлення через upsert** відхилено: воно створює відсутній запис при PUT і перезаписує дублі при POST.
- **CSS-бібліотека** не використовується за вибором користувача.

# Вимоги симуляції кол-центру: Чекліст

**Призначення**: Оцінити повноту, ясність і перевірюваність вимог до імітаційного прототипу кол-центру.
**Створено**: 2026-11-10
**Функція**: [Специфікація](../spec.md)

**Примітка**: Цей користувацький чекліст створено за контекстом функції та вимогами.
**Власник перевірки**: Чекліст є артефактом перевірки якості вимог, за який відповідає перевіряльник. Позначайте пункт `[x]` лише якщо вимогу визнано достатньо якісною.
**Значення позначок**: `[x]` означає, що критерій перевірки якості вимог розглянуто й задоволено; це не означає завершення реалізації.

## Повнота вимог

- [ ] CHK001 Чи охоплюють вимоги всі ролі та етапи наскрізного сценарію від заявки клієнта до підсумку? [Completeness, Spec §FR-001, US1]
- [ ] CHK002 Чи визначено, що демонстрація запускається автоматично, без введення, і використовує лише фіксовані вигадані дані? [Completeness, Spec §FR-012, FR-015]
- [ ] CHK003 Чи описує специфікація навчальне призначення, обмеження та очікуваний зміст інструкцій із запуску? [Completeness, Spec §FR-007, SC-006]
- [ ] CHK004 Чи охоплено всі зовнішні дії, які мають бути лише симульовані, а не виконані реально? [Completeness, Spec §FR-005, Assumption]

## Ясність вимог

- [ ] CHK005 Чи однозначно визначено назви та порядок усіх станів успішного сценарію? [Clarity, Spec §FR-002, SC-002]
- [ ] CHK006 Чи достатньо конкретно визначено умови створення запису, пов'язування оцінки з дзвінком і підготовки та надсилання підсумку? [Clarity, Spec §FR-003]
- [ ] CHK007 Чи визначено, що саме вважається успішним завершенням демонстраційного сценарію? [Clarity, Spec §US1, SC-002]
- [ ] CHK008 Чи визначена мінімальна підтримувана версія JDK узгоджено у вимогах і матеріалах запуску? [Ambiguity, Plan §Технічний контекст]

## Узгодженість вимог

- [ ] CHK009 Чи узгоджується основний шлях зі станами й переходами, описаними в діаграмах станів і послідовності? [Consistency, Spec §FR-002, FR-010]
- [ ] CHK010 Чи узгоджено межі стандартного успішного запуску з вимогою перевіряти негативні сценарії окремо? [Consistency, Spec §FR-013, FR-014, Clarifications]
- [ ] CHK011 Чи немає суперечностей між англомовними програмними ідентифікаторами та українськими повідомленнями, коментарями й документацією? [Consistency, Spec §FR-009]
- [ ] CHK012 Чи узгоджені вимоги до мінімальної складності, відповідальностей класів та передавання залежностей із конституцією? [Consistency, Spec §FR-008, Assumption]

## Якість критеріїв приймання

- [ ] CHK013 Чи можна об'єктивно встановити за критеріями успіху, що компіляція та запуск можливі командами з README лише за наявності JDK? [Acceptance Criteria, Spec §FR-006, FR-007, SC-001]
- [ ] CHK014 Чи вимірювано визначає критерій успіху порядок п'яти станів і повідомлення про завершення? [Measurability, Spec §SC-002]
- [ ] CHK015 Чи достатньо чітко визначено критерій відповідності класів, атрибутів, викликів, зв'язків і переходів документації? [Measurability, Spec §FR-011, SC-003, SC-004]

## Покриття сценаріїв

- [ ] CHK016 Чи визначені вимоги для основного шляху окремо для заявки, обробки оператором, оцінювання супервізором і підсумку клієнту? [Coverage, Spec §US1, US2, FR-001, FR-003]
- [ ] CHK017 Чи визначено очікуваний результат спроби оцінювання, коли запис розмови відсутній? [Coverage, Spec §FR-004, FR-013]
- [ ] CHK018 Чи визначено результат незавершеної обробки та заборону переходів до `Recorded` і `QualityEvaluated`? [Coverage, Spec §FR-014]

## Покриття граничних випадків

- [ ] CHK019 Чи визначено, які стани відмови з предметної моделі входять до обсягу, а які навмисно виключено: відхилена заявка, недоступний оператор, збій телефонії, оцінювання та надсилання підсумку? [Gap, Assumption, Data model §Call]
- [ ] CHK020 Чи описано наслідки відсутнього підсумку або непідтвердженого надсилання, зокрема щодо кінцевого стану дзвінка? [Gap, Data model §Call, FR-003]
- [ ] CHK021 Чи визначені вимоги до відхилення заявки з порожніми контактними даними та чи навмисно формат контактів залишено поза обсягом? [Gap, Data model §Client]
- [ ] CHK022 Чи визначено шкалу або межі оцінки якості, або прямо зазначено, що їх не задає ця функція? [Ambiguity, Data model §QualityEvaluation]

## Нефункціональні вимоги

- [ ] CHK023 Чи задокументовано, які нефункціональні вимоги застосовні до короткої локальної демонстрації, а які, зокрема продуктивність, не застосовуються? [Completeness, Plan §Технічний контекст]

## Залежності та припущення

- [ ] CHK024 Чи явно визначено, що JDK є єдиною зовнішньою передумовою, а бібліотеки, база даних, мережа й постійне зберігання не потрібні? [Assumption, Spec §FR-006, Assumptions]
- [ ] CHK025 Чи описано, як погоджені UML-діаграми та CRC-картки впливають на вимоги і як документуються узгоджені зміни до них? [Dependency, Spec §FR-010, FR-011, Assumptions]

## Примітки

- Позначайте `[x]` лише після оцінювання якості вимоги; нез'ясовані, неоднозначні або неповні пункти залишайте непозначеними.
- `/speckit-implement` читає стан позначок чекліста як умову, але не змінює їх.
- `checklists/requirements.md` має окремий життєвий цикл, який підтримують `/speckit-specify` і `/speckit-clarify`.
- Додавайте зауваження або посилання на відповідні матеріали під час перевірки.

# Дослідження: Імітаційний прототип кол-центру

## Висновок

Специфікація й наявні UML/CRC-артефакти визначають предметну модель і потрібну поведінку. Реалізацію можна виконати стандартним JDK без фреймворку, залежностей, бази даних, зовнішніх інтеграцій або невирішених технічних припущень. Версію JDK 8 обрано як консервативну нижню межу: план не потребує новіших мовних можливостей чи API; у README необхідно назвати передумову JDK 8+.

## Рішення

### Технологія та структура

- **Рішення**: Java 8+, стандартна бібліотека; джерела застосунку в `src/main/java/callcenter`, перевірки в `src/test/java/callcenter`; компіляція `javac`, запуск `java`.
- **Обґрунтування**: виконує FR-006 і конституційні вимоги до командного запуску та відсутності зовнішньої інфраструктури. Така структура відділяє точку входу, предметну модель та перевірки без додаткового інструментарію.
- **Розглянуті альтернативи**: Maven/Gradle, сторонні тестові фреймворки та DI-контейнер. Відхилено, бо вони додають залежності й не потрібні для малого прототипу.

### Модель і життєвий цикл

- **Рішення**: реалізувати погоджені класи й відносини з `docs/class.mmd` та відповідальності з `docs/crc.xlsx`; захищати переходи стану всередині `Call` перевіркою потрібної попередньої умови. Виводити точні назви станів з `docs/state.mmd`.
- **Обґрунтування**: UML і CRC є джерелом предметної моделі за припущеннями та FR-010/FR-011; інкапсуляція переходів не дозволяє повідомити успіх перед створенням запису, збереженням оцінки чи підтвердженням надсилання.
- **Розглянуті альтернативи**: рядкові зміни стану з ролей/служб без централізованої перевірки, або додаткові архітектурні шари. Перше послаблює контроль переходів, друге невиправдано збільшує складність.

### Демонстрація та зовнішні дії

- **Рішення**: один автоматичний успішний запуск із фіксованими вигаданими даними; результати симуляції телефонії та пошти виводяться українською. Успішний сценарій використовує послідовність `NewRequest` → `CallInProgress` → `Recorded` → `QualityEvaluated` → `SummarySent`.
- **Обґрунтування**: прямо відповідає FR-001—FR-005 та FR-012—FR-015; повторюваний вивід не вимагає введення або зовнішніх послуг.
- **Розглянуті альтернативи**: випадкові/реальні дані, інтерактивний ввід, реальні виклики або включення невдалих випадків до звичайного запуску. Відхилено специфікацією та навчальними обмеженнями.

### Перевірки відмов

- **Рішення**: перевірити обмеження життєвого циклу окремим JDK-only виконуваним класом. Для невдалого зовнішнього результату використовувати тестову підстановку симульованої служби, не змінюючи фіксований успішний сценарій.
- **Обґрунтування**: виконує окрему перевірку двох граничних випадків і не додає бібліотек чи режимів запуску до демонстраційного сценарію.
- **Розглянуті альтернативи**: ручна перевірка лише за консольним виводом або показ помилок під час кожного запуску. Перше не дає відтворюваного доказу передумов, друге суперечить FR-013/FR-014.

### Зовнішній контракт

- **Рішення**: описати консольний інтерфейс у [contracts/console.md](contracts/console.md): запуск без підтримуваних аргументів, автоматична демонстрація та обов'язковий порядок успішних станів.
- **Обґрунтування**: CLI є інтерфейсом користувача й запуск через README — критерій приймання.
- **Розглянуті альтернативи**: HTTP/API-контракти чи окремий протокол служб. Відхилено: застосунок не відкриває мережевого інтерфейсу, а служби лише симулюються.

## Перевірка невідомих

Специфікація не вказує версію Java, але не вимагає функцій новіших за Java 8; тому нижню межу зафіксовано як JDK 8+. Інші параметри запуску та моделі даних задаються специфікацією і наявними діаграмами. Зовнішніх технічних невідомих, що блокують дизайн, немає.

# Дослідження: збереження даних кол-центру

## Рішення 1: Maven і структура Java

**Рішення**: один Maven-проєкт `callcenter`, структура `src/main/java` та `src/test/java`, версія компіляції задається як Java 21 через `maven.compiler.release`. Файли збірки й звіту розміщуються у `target`.

**Обґрунтування**: така структура є стандартною для Maven, а `target` призначений для результатів збірки. JDK 21 забезпечує компіляцію в цільову версію та виконання проєкту. У робочому оточенні Maven відсутній, тому встановлено офіційний Apache Maven 3.10.0 у профіль користувача й додано його `bin` до користувацького `PATH`; Maven підтвердив запуск на JDK 21.0.6.

**Розглянуті альтернативи**: зберегти ручну компіляцію `javac` або додати Maven Wrapper. Ручна збірка не відповідає вимогам; Wrapper не потрібен для заданого середовища й команди Maven.

**Джерела**:
- [Maven Standard Directory Layout](https://maven.apache.org/guides/introduction/introduction-to-the-standard-directory-layout.html)
- [Apache Maven Downloads and installation guidance](https://maven.apache.org/download.cgi)

## Рішення 2: Google Guice 7 і створення `Call`

**Рішення**: `CallCenterModule` успадковує `AbstractModule`, зв'язує `RecordingStore` із `SqliteRecordingStore` і надає JDBC-з'єднання. `Call` має `@Inject`-конструктор для `RecordingStore` та вже потрібних йому сценарних об'єктів. Модуль отримує наявні екземпляри `Client`, `Operator`, `TelephonyService` і ідентифікатор виклику як контекст одного демонстраційного запуску та зв'язує їх; `Main` створює Injector і отримує `Call` через `injector.getInstance(Call.class)`. `Client` отримує перевантаження `requestCallback`, яке приймає цей `Call` і зберігає наявні повідомлення та перевірку контактів. Поточні сигнатури залишаються сумісними для наявних перевірок.

**Обґрунтування**: Guice створює об'єкти через позначений `@Inject` конструктор і вирішує їхні залежності на основі зв'язувань модуля; точка входу створює Injector і запитує цільовий об'єкт через `getInstance`. Так Guice керує створенням `Call`, а телефонія й електронна пошта залишаються звичайними симульованими об'єктами, без нового DI-графа для решти застосунку. Перевантаження методу клієнта дозволяє зберегти консольний сценарій і не створювати `Call` у `Main` чи у новому фабричному рівні.

**Розглянуті альтернативи**: статичний доступ до сервісу (порушує конституцію), пряме створення `Call` у точці входу (порушує вимогу Guice), або AssistedInject/окрема фабрична підсистема (додаткова залежність і складність для одного сценарного `Call`). Додатковий модуль AssistedInject не планується, якщо можна зберегти обмеження специфікації простішим зв'язуванням Guice.

**Джерела**:
- [Guice Getting Started: constructor injection, modules, Injector](https://github.com/google/guice/wiki/GettingStarted)
- [Google Guice 7.0.0 release](https://github.com/google/guice/releases/tag/7.0.0)

## Рішення 3: SQLite через sqlite-jdbc

**Рішення**: Xerial `sqlite-jdbc` як Maven-залежність; JDBC URL вказує на `target/callcenter.db`. З'єднання та ресурси JDBC закриваються за допомогою try-with-resources. SQL-схема й підготовлені запити належать лише `SqliteRecordingStore`; повторне збереження використовує конфлікт первинного ключа для оновлення.

**Обґрунтування**: драйвер надає стандартний JDBC-доступ до локального файла та постачає нативні бібліотеки для поширених ОС в артефакті. Локальний файл відповідає вимозі роботи без сервера. Відокремлення SQL у сервісі відповідає конституції.

**Розглянуті альтернативи**: база в пам'яті (дані не переживають запуск), файлова серіалізація (не SQLite і немає SQL-інтерфейсу), зовнішній сервер (заборонений обсягом і конституцією).

**Джерело**:
- [Xerial sqlite-jdbc README](https://github.com/xerial/sqlite-jdbc)

## Рішення 4: звіт і тестування

**Рішення**: генератор читає весь набір `CallRecording` через предметний інтерфейс і створює `target/callcenter-report.html`. Текстові значення екрануються для HTML-контексту. Для автоматизованих перевірок Maven використовується JUnit Jupiter; також зберігається наявна перевірка життєвого циклу.

**Обґрунтування**: звіт є статичним, не потребує сервера чи браузера під час генерації; екранування запобігає інтерпретації даних як розмітки. JUnit Jupiter інтегрується зі стандартною Maven-фазою тестування й дає змогу перевірити upsert, повторне читання, порожню вибірку та HTML-екранування.

**Розглянуті альтернативи**: формувати розмітку в SQL-сервісі або доменному класі (порушує SRP), відображати дані через вебсервер (зайва інфраструктура), покладатися лише на ручну перевірку (не дає відтворюваної перевірки Maven).
